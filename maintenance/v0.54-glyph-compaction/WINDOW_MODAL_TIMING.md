# v0.78 窗口移动与缩放后的计时恢复

## 问题与改动

Windows 拖动标题栏和边框会进入移动/缩放消息循环。v0.77 只在客户区尺寸改变并重建渲染器时重置物理计时；移动窗口、取消缩放或拖回原尺寸可能绕过该路径。等待时间随后被计入一帧，污染滚动帧时及 benchmark，物理最多补算 8 个 10ms 步长。

v0.78 在 WM_EXITSIZEMOVE 设置一次性恢复标志并再次暂停键盘输入。主循环在采样之前排除该间隔，然后清空物理余量、设置 dt=0、清除活动标志，消费恢复标志。下一条干净边界建立后恢复采样。保留真实 wallElapsed 时间线；不丢弃普通渲染慢帧，也不重置此前有效的 benchmark 样本。原生菜单已有恢复逻辑保留。

没有增加画质、贴图、渲染开销或存档字段。此前 v0.72 窗口标题、帮助和启动日志标识同步为 v0.78，CMake 与 benchmark 标识一致。

微软消息语义参考：https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-exitsizemove 。此文档说明消息时机，不代表本项目已完成 Windows 消息投递实测。

## 可重复检查

运行 `python3 tools/check_window_timing.py`：从实际 main.cpp 提取退出消息处理与计时语句，编译 C++17 CPU 检查。12 组覆盖 benchmark 开/关、渲染器重建/不重建及 0.001/1/30 秒模拟间隔；另查普通慢帧、原生菜单、恢复后采样和按键释放重按规则。Win32 API 由测试替身提供。

可传入上版 main.cpp 重现失败；旧版能编译，但在“不改变客户区尺寸也必须丢弃物理等待时间”断言失败。新版正常及 ASan/UBSan 结果见 validation_v078。初写测试误用了不存在的 BenchmarkSamples::values，改为公开 storedSamples() 后才开始有效的新旧对照；该编译错误不作为旧版缺陷证据。

1. 使用包含资源的 Release 构建启动 DX11，记录 startup.log、版本、分辨率、驱动和系统信息；再检查可用的 DX12 路径。
2. 飞行中按住标题栏 10 秒后松开；再尝试拖边框后 Esc 取消、拖回相同尺寸、改变尺寸、系统菜单“移动/大小”。核对恢复时飞机没有等待时间补算，仍可继续操纵。
3. 分别在 benchmark、普通模式及省电模式操作，检查 performance.csv 和 benchmark 原始记录：等待间隔不计入飞行样本，之后正常采样；真实渲染慢帧仍保留。
4. 检查原生菜单、切出窗口、最小化以及松开重按 W/G；验证不重放旧输入。
5. 在 i5-5350U / HD6000 / 8GB 目标机记录前台帧时、内存、温度、启动耗时和完整航班录像。本轮无该设备连接，尚未执行。

这是恢复计时与诊断准确性修复，不是 FPS、功耗或画质提升实测。项目仍是原型，不能据此确认成品。
